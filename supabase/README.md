# База данных

## Что здесь лежит

- **`migrations/`** — единственный источник правды. Файлы применяются по возрастанию
  имени, то есть по временной метке в начале имени. Имена и порядок совпадают
  с `supabase_migrations.schema_migrations` в боевом проекте.
- **`functions/`** — edge-функции (пуши, ИИ, превью ссылок).
- **`email-templates/`** — письма подтверждения и восстановления доступа.
- **`schema.sql`** — **исторический слепок** самой первой версии схемы. Он НЕ
  отражает текущее состояние базы и оставлен только для чтения истории.
  Никогда не накатывайте его на живой проект.

## Как менять схему

1. Изменение применяется как миграция (`apply_migration`), никогда как голый SQL
   в консоли: иначе у него нет имени и оно не воспроизводится.
2. Тот же SQL коммитится сюда файлом `<version>_<name>.sql`.

Если пункт 2 пропустить, репозиторий тихо расходится с базой — именно это и
произошло с 24 миграциями с 29 июля по 31 июля 2026 года, которые были
восстановлены из живой базы задним числом.

## Жёсткие правила

- Никаких `using (true)` в RLS-политиках.
- Политика таблицы T не делает подзапрос к T — это бесконечная рекурсия.
  Нужна функция `security definer` (см. `fc_is_admin`, `fc_is_post_in_chat`).
- Секретов в файлах нет. Ключи живут в Vault и читаются через
  `vault.decrypted_secrets`.
- Функция, которая должна видеть только то, что видит вызывающий (например
  `search_messages`), обязана быть `security invoker`.
